# Account credentials and password notifications

## Password selection and verification

Registration, authenticated password changes and account-recovery password selection require at least eight characters, using the same length rule. Rejected input stays on the password-selection step and does not replace the pending hash or move to confirmation.

This policy applies when selecting a replacement password. Existing shorter passwords still verify through the unchanged legacy salted SHA-384 representation. This change does not migrate password hashes, introduce token expiry or invalidate authenticated sessions.

Debug support login remains intentionally passwordless for reproducing player-reported account/character issues. Public Release login continues to verify the password. Debug builds are not public release products.

## Generated credentials

Registration codes, recovery codes and staff-generated temporary passwords use `SecurityUtilities.GetRandomString`, which now selects each character with `RandomNumberGenerator.GetInt32`. Authentication credentials no longer consume the simulation PRNG or its seeded test scopes. Existing alphabets and requested lengths are unchanged; existing stored codes are not regenerated by an upgrade.

## Password-change notification compatibility

`EmailHelper.SendPasswordChangedEmail` receives only the recipient address, account name and IP address. It does not receive the replacement password. MIME composition also discards any old caller's third argument for `AccountPasswordChanged`, before creating or queueing the message.

The template arguments are:

| Placeholder | Value |
| --- | --- |
| `{0}` | Account name |
| `{1}` | IP address from the existing notification caller |
| `{2}` | The fixed text `not included in email` |

The third argument is retained for compatibility indefinitely. Existing three-placeholder templates still format, including customised HTML. Templates using only `{0}` and `{1}` work too. Escaped braces retain normal composite-format semantics. Other invalid placeholders remain formatting errors handled by the email subsystem.

Fresh installations receive a password-change template that uses only the account name and IP address, tells the player to use their selected password, and explains that the notification does not include it. Existing database template bodies, subjects and return addresses are not overwritten, either by email configuration loading or Core seeder reconciliation. No schema migration or seeder rerun is required.

Operators can optionally edit an older template to remove wording such as “your password is now {2}” and use a simple change notification instead. Until then, the old sentence may sound awkward, but the message is still delivered without the password. No credential is substituted into the compatibility slot.

This change is limited to `AccountPasswordChanged`. The separate HighAdmin `resetpassword` workflow still emails its generated temporary password using `AccountPasswordReset`. Its arguments and notification behavior are unchanged.

For transports, configuration, retries and failed-message storage, see [Outbound Email Delivery](Outbound_Email_Delivery.md).
