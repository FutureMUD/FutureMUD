# Employment task restart and recovery

Status: current runtime and persistence contract, source reviewed 17 November 2026. Focused runtime checks, independent real-MySQL writer/reader processes, and live Telnet crash/restart scenarios are recorded below.

This guide covers persisted active-task approvals and interrupted financial work. See the [employment roadmap](Employment%20Hosts%20Implementation%20Review%20and%20Roadmap.md) and [unified dispatch design](Unified%20Employment%20Dispatch%20Design.md) for the broader system. Historical readiness statements are retained as dated receipts, not current verification.

## Durable task approval

Active tasks now persist a version-1 approval/provenance document in `EmploymentActiveTasks.ProvenanceJson`. It binds the task and correlation IDs, host type and ID, provenance, grant, and a SHA-256 binding of the ordered persisted action-step fields. Task state saves update this document alongside step state. A separate immediate transaction is used for audited approval changes, with the expected grant ID and revision checked against stored state and the current ordered plan checked before commit. The approval document is stored on the task row; action-plan configuration and step-state rows remain separate.

The document preserves source kind and source rule/goal, creator and authoriser principals, grant identity/revision, authority, amount limits by currency ID, the unbounded-financial-step flag, payment-source and counterparty scopes, issuance time, expiry/revocation state, priority and task timestamps, as well as recovery state. A finite currency limit covers the remaining cumulative amount in that currency; an absent currency limit permits it only when unbounded financial steps are explicitly allowed. Scope values are normalized case-insensitively; an empty source or counterparty scope set means unrestricted scope, while a nonempty set requires a matching known scope. Manager goals persist a versioned approval configuration containing the authorising principal, condition expression, risk limits and currency budgets. Scheduled rules persist their approval principal. The schema columns are `ProvenanceJson`, `ApprovalPrincipalJson`, and `ApprovalConfigurationJson`; migration `20261117030326_PersistEmploymentTaskApprovals` adds them.

On load, version, task/host/correlation identity, grant structure, plan binding, action-step reconstruction, and step-state order are checked. The version-1 document is limited to 1 MiB; amount-limit currency IDs must be positive, amounts nonnegative, grant revision positive, and any expiry later than issue time. Missing legacy provenance is treated as an empty legacy approval, not inferred authority. Malformed, unsupported-version, identity/plan-mismatched, or unmappable evidence is quarantined and retained for inspection; loading never mints approval. Recovery does not automatically reconstruct provenance already lost from older rows.

Before a financial step runs, the task grant must cover the step and be unrevoked and unexpired. Approval issue, expiry and revocation timestamps use real UTC (`DateTimeOffset.UtcNow`), independent of the game clock; task lifecycle, due and priority timestamps retain the existing `EmploymentClock` representation. The issuer must still resolve and retain the required authority; a stored employment contract must remain active. Scheduled-rule and manager-goal identities are provenance only, never human financial authorisers. Host-system approval is accepted only when explicitly stored as the authority principal. These checks apply to task-bound financial work; standalone host operations retain their native authority checks.

Completed action steps are not natively executed again. Their authorised amounts remain charged against the original cumulative limit when later financial steps are checked. A confirmed-executed purchase or physical-float step whose durable task state has neither `SelectedResources` nor `LoadedAssets` remains held: native inventory/cash repair alone cannot satisfy the task-custody evidence guard. Current commands cannot attach the missing task custody evidence or waive this guard. Do not use reconciliation to bypass it; the case requires separate task-custody repair tooling.

## Approval inspection and audited recovery

Use the host's shared employment task command surface:

```text
tasks approval show <task>
tasks approval revoke <task-id> <grant-id> <revision> <reason>
tasks approval replace <task-id> <grant-id> <revision> <never|ISO-8601-expiry> <reason>
tasks approval reconcile <task-id> <grant-id> <revision> <step-number> <executed|not-executed> <evidence-reference> <reason>
tasks retry <task> <reason>
tasks requeue <task> <reason>
```

`show` reports the grant, issuer, scopes, limits, expiry/revocation state, uncertain financial steps, the explicit-retry requirement and quarantine issue. Approval mutations require `AssignTasks` plus every authority required by the original plan, the exact current task/grant IDs and grant revision from `show`, and an audit reason. Replacement expiry is either `never` or a round-trip ISO-8601 timestamp with explicit offset. A replacement preserves the existing authority, limits and scopes, completed-spending history, and reconciliation holds. A legacy task may be explicitly replaced using its authored plan limits; that replacement is an audited new approval and does not claim to recover the old one.

Interrupted financial steps are held for manager review. The dispatcher flushes native financial `SaveManager` work before persisting a completed task-step state; a crash between native commit and completion state therefore leaves the step `InProgress` for reconciliation. Such a step is considered uncertain when it is financial or requires payment authorisation, even if no payment-completed flag was saved. Reconciliation records whether the external/native operation executed, an evidence reference, reason, actor and grant revision. Confirmed executed steps are marked complete without repeating their native operation; confirmed not-executed steps become eligible for the ordinary task retry path. Reconciliation itself never issues payment, retries the task, or clears other holds. If work remains, reconciliation persists `RequiresExplicitRetry` in the existing provenance document and keeps the task blocked across saves and restarts. Assignment auditing, worker claiming and manual assignment cannot clear this requirement. An authorised `tasks retry` or `tasks requeue` with an audit reason clears it only after financial and custody holds are resolved. These lifecycle commands require `AssignTasks`; financial execution still checks the unchanged task approval and current authority. `retry` can also reset an ordinary failed step, while `requeue` does not reopen failed tasks. For executed purchase/physical-float steps with missing durable task-custody evidence, this command cannot complete reconciliation; native repair alone does not provide the required `SelectedResources`/`LoadedAssets` task evidence, and the guard must not be waived. Cancellation does not erase the idempotency key while financial outcome remains uncertain.

Revocation, replacement and reconciliation are audited through employment register entries and persisted with the task transition. Ordinary task-state saves also compare the stored grant identity/revision, so an older task object cannot restore revoked approval or undo a newer reconciliation. They are optimistic-concurrency guarded by the approval grant ID/revision and plan binding. A stale view must be refreshed before another mutation.

## Operator workflow

1. Inspect the task and its approval after restart. Check its plan, grant status, assignment, step states, operational custody and any recovery/quarantine messages.
2. If a financial step is uncertain, compare the task evidence with the native payment, inventory, bank or host ledger. Do not retry until its outcome is known.
3. Use `reconcile` with an evidence reference and reason to record that outcome when the task has the required custody evidence. If an executed purchase/physical-float step has neither durable `SelectedResources` nor `LoadedAssets`, it remains held; native custody repair does not clear that task-evidence guard and current commands cannot attach the missing evidence.
4. If approval is expired, revoked, or the original issuer has lost authority, obtain a fresh audited replacement from an actor authorised for task assignment and the full original plan authority. Approval replacement alone does not resume or retry work. For pre-migration scheduled rules or manager goals with no persisted issuer, no issuer is inferred: re-create/re-author the source under an authorised manager for future financial tasks, or explicitly replace the approval on an already spawned legacy task.
5. If work remains, use `tasks retry <task> <reason>` or `tasks requeue <task> <reason>` after recovery holds are resolved and the outcome is known. Approval replacement and assignment do not acknowledge this explicit recovery decision. Diagnostics bind the preview to the actual task and include an interrupted step in its visible step number.

At shops, the host-specific `shop tasks` and `shop register` views remain useful for operational and financial context. Approval commands are part of the shared task command service; other hosts use their respective employment prefix and authority rules.

## Limits and verification status

This contract prevents the system from silently treating absent, malformed, changed-plan, expired, revoked, or no-longer-authorised approval as valid. It does not automatically repair previously lost provenance, prove exactly-once semantics for every native host action, or certify general game stability. Recovery decisions rely on operator-supplied evidence and native subsystem records. The provider scenario qualifies task approval persistence and native bank-transfer recovery across independent test-host processes. The separate live Telnet qualification below covers full server startup, approval commands and native linked-bank transfers through an NPC worker. Neither scenario qualifies every host payment path or missing item/cash custody repair. Older fail-closed tests and historical readiness reports do not certify this implementation.

### Live Telnet follow-up, 17 November 2026

The actual Debug MUD was run against a freshly seeded, owned loopback MySQL world with a real shop, linked bank accounts, and a permanently hired NPC using `EmploymentWorkerAI`. Two task-specific pauses captured the native bank-transfer crash windows, with the MUD stopped before removing each temporary trigger. Graceful shutdowns and intentional process crashes were both exercised. Game time was frozen while real-UTC approval expiry was checked.

| Scenario | Observed result |
| --- | --- |
| Approval inspection, revoke and replace | Exact grant/revision and reason validation worked; stale revisions and invalid expiry were rejected; original limits/scopes survived restart and replacement. |
| Legacy, revoked, expired and unsupported approval | No silent payment. Legacy work needed an explicit bounded replacement; unsupported version-2 evidence remained intact and quarantined. A task whose NPC issuer lost authority was ineligible. |
| Crash after native payment, before completed checkpoint | The 3-farthing transfer committed once, with one debit and one credit. Restart held step 3; retry/requeue and replacement could not clear it. Evidence-backed `executed` reconciliation completed the task without another payment. |
| Crash before native payment, after started checkpoint | The 4-farthing transfer had no native records and balances remained 97/3. `not-executed` reconciliation set the persisted explicit-retry requirement. Worker auditing and a cold server restart left it blocked. |
| Explicit recovery | A forced ordinary employee and a reasonless administrator retry left the hold unchanged. An authorised retry with a reason cleared the requirement and the NPC completed the 4-farthing transfer once. Completed tasks rejected retry/requeue. |
| Subsequent cold restarts | Both tasks retained all three completed checkpoints. Balances stayed 93/7 from the original 100/0; each transfer still had exactly one paired native debit/credit. Reconciliation references and explicit-retry audit entries survived. |
| Cleanup | No temporary crash triggers remained. The owned MUD and MySQL processes were stopped; disposable data and evidence were preserved. |

Qualification found and corrected task diagnostics that did not bind the real task approval context, omitted the interrupted step number, or described the old worker cadence. It also exposed the missing shared retry/requeue command route and an assignment audit that could resume reconciled work without an explicit retry. A durable `RequiresExplicitRetry` flag now blocks worker claiming, assignment auditing and manual assignment until recovery is acknowledged. Focused review identified the nonfinancial-followup manual-assignment bypass, which was corrected and covered by a regression. The flag uses the existing provenance JSON column, defaults to false for older version-1 documents, and requires no further schema migration.

The live `not-executed` command initially failed because `PopForSwitch()` removes hyphens. Its outcome token now uses quote-aware speech parsing and case normalization while preserving the documented spelling. Both reconciliation outcomes are exercised through the command service in the existing regression cases.
