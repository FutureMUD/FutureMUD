# Item lifecycle review, 17 November 2026

Reviewed engine revision `5454794020cbf43ed85cf93392f42d52300f2a53`. The [lifecycle guide](Item_Lifecycle.md) models creation, rehydration, registration, placement, activation, suspension and retirement. This record gives the failure conditions, observed consequences and checks needed for repairs. Runtime code was unchanged during this examination.

## Findings reproduced in isolation

### 1. Revising an existing item can erase unrelated durable state

**High priority, persisted data loss.** `GameItem.CheckPrototypeForUpdate` attaches a sparsely populated item row when the old prototype is revised or obsolete. It marks the **whole entity** modified, then marks the quality and revision properties modified. The second step leaves the other mapped properties marked for update. The item builder's update pass calls this method and saves the context. [Revision implementation](../../MudSharpCore/GameItems/GameItem.cs) · [Maintenance caller](../../MudSharpCore/Commands/Modules/ItemBuilderModule.cs)

The probe seeded an item at revision 0 with owner 6, condition 0.9, skin 3 and 120 morph seconds, cleared EF tracking, constructed the native item from the stored row, ran the native revision update and read the row again. Revision 1 was stored with **null owner, condition 0, null skin and null morph time**. This used the repository's EF model and in-memory provider. Inspect the generated SQL and round-trip a disposable MySQL row when repairing the update. The repair criterion is that every unrelated persisted field survives, including fields the live item has yet to materialise.

The same method introduces newly required components with `CreateNew` and refreshes the media index, but does not call their `FinaliseLoad` or `Login`. A live repair must activate an added component once according to the parent's current state, while preserving dormancy for an offline maintenance target. The existing media test covers index membership on add/remove. [Index coverage](../../MudSharpCore%20Unit%20Tests/StartupLookupIndexTests.cs)

### 2. An electrical grid can resolve an unrelated producer on reload

**High priority, incorrect power topology.** `ElectricalGrid.SaveDefinition` writes `producer.Id` and `consumer.Id`, which are **component IDs**. `LoadTimeInitialise` looks through floor items in grid rooms by **item ID**, then selects the first component of the corresponding interface. The lookup silently skips misses. Outlet, supply and feeder components can also join their grid while reading their own XML. That second path can hide the missing lookup or add a second membership. Grid lists accept duplicates and `TotalSupply` sums every producer entry. This is the concrete electrical implementation returned by the grid factory. [Grid writer and loader](../../MudSharpCore/Construction/Grids/ElectricalGrid.cs) · [Grid factory](../../MudSharpCore/Construction/Grids/GridFactory.cs) · [Feeder membership](../../MudSharpCore/GameItems/Components/ElectricGridFeederGameItemComponent.cs)

With a **100 W** producer component 102 on item 42, the native writer emitted `<Producer>102</Producer>`. Reloading that XML with only item 42 in the grid room yielded **0 W**. Adding unrelated floor item 102 with a **13 W** producer yielded **13 W**. This isolates the grid-side restore path. It does not measure aggregate supply in a setting where the correct feeder also self-registers. Repairs need a version-aware key, exact endpoint selection and one reconciliation of the two sources. A blind fallback from component ID to item ID will still accept numerical collisions.

### 3. A running fuel generator outlives logout and deletion

**High priority, live callback after teardown.** Fuel restoration can call the ordinary switch/fuel setters. `FinaliseLoad` also subscribes a switched-on generator to the second heartbeat. `Quit` propagates to locks and `Delete` deletes locks. Neither removes the generator's subscription. Destroying item schedules cannot remove this delegate from the heartbeat manager. Its callback mutates the liquid mixture and can invoke the fuel-out prog and notify consumers. [Generator](../../MudSharpCore/GameItems/Components/FuelGeneratorGameItemComponent.cs) · [Heartbeat registration](../../MudSharpCore/Framework/Scheduling/HeartbeatManager.cs)

With 10 fuel units and a one-unit burn per tick, invoking the still-registered handler once after component quit left **9**. The component's dirty flag stayed false after this partial burn. One tick after component deletion left **8**. The fixture replayed event registration with the native manager's one-entry-per-delegate semantics. A fix must preserve the durable on/off selection, checkpoint fuel consumption, release external registrations in both teardown paths, and reacquire exactly once on login. Include an unpublished copy of an operating generator since its copy constructor also uses live setters.

### 4. World login reaches nested items twice and can fail when a child removes itself

**High priority, boot reliability and duplicate side effects.** The loader snapshots **all** registered items for login. Ordinary container XML looks up contained item IDs with registration enabled, and a container's `Login` also calls each contained item's `Login`. The item graph's finalisation guard does not apply to activation. An analogous traversal exists for mounted modules. Each additional owning ancestor that recursively forwards login is another entry path. [Loader](../../MudSharpCore/Framework/FuturemudLoaders.cs) · [Container](../../MudSharpCore/GameItems/Components/ContainerGameItemComponent.cs) · [Mount host](../../MudSharpCore/GameItems/Components/AutomationMountHostGameItemComponent.cs)

The same traversal produced three different consequences in isolation.

- Running the production `IFuturemudLoader.LoadWorldItems` phase with a pre-registered container and child delivered **two** child logins. The fixture began at the state normally left by room staging, used the native container XML loader and component lifecycle, and counted calls on the child. It had no database room rows, shops or grids.
- The container enumerates its live contents list. A child callback removing itself through `Container.Take` produced **“Collection was modified; enumeration operation may not execute.”** An overdue armed trigger is a concrete path to the same mutation, through `Detonate` and `Parent.Delete`. The probe exercised removal during traversal, not an explosion simulation. The outer `GameItem.Login` also only checks `Deleted` at entry, so a component that deletes the parent can leave later siblings or effects running on a retired item. [Deadline](../../MudSharpCore/GameItems/Components/DeadlineExplosiveTriggerGameItemComponent.cs) · [Bomb](../../MudSharpCore/GameItems/Components/BombGameItemComponent.cs)
- A handheld radio requests sibling drawdown on every login. With the native prog supply, two begins, one end and a subsequent off/on cycle produced **three** cut-ins in total. The third came **after** the single detach. The supply uses lists and removes one entry. A battery-powered producer has its own deduplication, so the result depends on component composition. [Radio](../../MudSharpCore/GameItems/Components/HandheldRadioGameItemComponent.cs) · [Prog supply](../../MudSharpCore/GameItems/Components/ProgPowerSupplyGameItemComponent.cs) · [Battery-powered producer](../../MudSharpCore/GameItems/Components/BatteryPoweredGameItemComponent.cs)

Choose a single activation owner per live interval and keep recursive traversal safe. A room-roots-only patch would miss independent peers. A snapshot by itself still delivers duplicate logins and can activate stale children. Test a shared peer, a nested owner, a self-deleting child and a fresh login after a real quit.

### 5. One restored timed effect receives two login notifications

**Medium priority, effect-specific side effects.** The item loops over all its effects and calls `Login`. Then `ScheduleCachedEffects` reschedules each cached effect and calls its `Login` again. Cached effects are already in the same effects collection. With a five-minute cached duration, a single native item login delivered **two** effect login notifications. This occurs independently of the nested-item duplication above. An idempotent effect may mask it. A subscriber, emitter or one-shot effect may behave differently. [Item login](../../MudSharpCore/GameItems/GameItem.cs) · [Effect cache](../../MudSharpCore/Framework/PerceivedItem.cs)

The ordering matters to a repair. For example, an expiring description addition reasserts its absolute UTC deadline in its login callback. Deliver the callback once at the correct point relative to rescheduling. Include an effect that removes itself and check the live effect list remains safe to traverse. [Absolute expiry implementation](../../MudSharpCore/Effects/Concrete/DescriptionAddition.Expiry.cs)

### 6. A detached instance can unregister a different instance with the same ID

**High priority where detached objects cross lifecycle boundaries.** A default `TryGetItem(id)` can construct an unregistered object. A later registered lookup can construct another native instance for that ID. `Futuremud.Destroy(IGameItem)` passes the supplied instance to `All.Remove`, which checks the key and removes it without confirming that the dictionary currently maps to that object. Native item equality also accepts matching initialised IDs. In a native registry containing one item 44, removing a distinct, detached instance 44 made the registered item **unresolvable**. The probe exercised the collection operation used by quit/delete. It did not delete a database row. [Lookup and destruction](../../MudSharpCore/Framework/Futuremud.cs) · [Removal](../../MudSharpCore/Framework/All.cs) · [Item equality](../../MudSharpCore/GameItems/GameItem.cs)

Construction-only lookups also have external costs when a component subscribes during load. Test detached inspection followed by later activation, and releasing the old object while the new object is live. Reference-aware unregistration protects registry membership. A separate decision about which instance may persist or delete is needed to protect storage.

### 7. A severed-bodypart copy can delete the source's children

**High priority, destructive aliasing.** The component copy constructor creates new lists for contents, implants and wounds, but puts the original object references in those lists. Its delete path iterates those objects and invokes their native deletion operations. The probe copied a component containing one child using the ordinary permanent `Copy` path. The copy held **the exact original child**. Deleting the copy called that child's `Delete` once, while the source still listed it. This exercised native component copy and teardown with a counting child. [Severed bodypart](../../MudSharpCore/GameItems/Components/BodypartGameItemComponent.cs)

The general `DeepCopy` path introduces a second problem here. After making the component copy it recursively clones ordinary container contents and calls `Put` on the new container. A severed part implements `IContainer`, but its `Put` throws unconditionally. A populated permanent copy can therefore fail after publishing objects. Define which bodypart state and children can be independently cloned, or refuse the operation before allocating/publishing. Include deletion of each resulting item in the acceptance test and verify that its counterpart remains usable. [Deep copy](../../MudSharpCore/GameItems/GameItem.cs)

## Additional findings from source tracing

These paths were traced to their callers. The consequences below depend on the stated data or component composition.

| Priority and path | Trigger and consequence | What to verify in a repair |
| --- | --- | --- |
| High · Recursive construction | A stored container names itself or two containers name one another. `TryGetItem` registers only after `new GameItem(row, world)` returns, while the container XML constructor recursively calls `TryGetItem`. The same ID can re-enter construction before either the registry or the finalisation guard covers it. Unbounded recursion can terminate startup. No stack-overflow experiment was run. [Lookup](../../MudSharpCore/Framework/Futuremud.cs) · [Container loader](../../MudSharpCore/GameItems/Components/ContainerGameItemComponent.cs) | Reject self/ancestor ownership during resolution by ID. Preserve legitimate reciprocal, non-owning connections. Diagnose the path of IDs and avoid publishing a partially initialised parent. |
| High · Conflicting custody | Generic containers accept an apparently unattached child even if its stored `ContainerId` points elsewhere. The first materialised claimant can win. Ammo clips adopt XML children with fewer custody checks, so a second owner can still hold the same reference in its list. Recursive deletion through a stale list can reach someone else's child. The internal-magazine loader shows a stricter check against the stored parent ID. [Ammo clip](../../MudSharpCore/GameItems/Components/AmmoClipGameItemComponent.cs) · [Magazine restore](../../MudSharpCore/GameItems/Components/InternalMagazineGunGameItemComponent.cs) | Load both orders with duplicate, missing, legacy-null and conflicting parent IDs. Require one owner or an explicit recoverable quarantine before destructive actions. A skipped record or a warning during `_noSave` does not prove the stored XML was repaired. |
| High · Replacement publication | `LoadMorphedItem` creates a normal item. The timed `Morph` path swaps or places and logs it in without an explicit world add. Ordinary room/zone insertion updates spatial collections. The native container swap only replaces custody. A clean unregistered replacement can therefore be visible in the container/room yet absent from global ID lookup and world indexes. In damage death, the replacement **is** added, but successful container swap or component-handled relocation returns before the final login/event pair. [Morph](../../MudSharpCore/GameItems/GameItem.cs) · [Replacement factories](../../MudSharpCore/GameItems/GameItemProto.cs) · [Damage death](../../MudSharpCore/GameItems/GameItemHealth.cs) · [Container swap](../../MudSharpCore/GameItems/Components/ContainerGameItemComponent.cs) | For each floor/held/contained replacement, verify the exact object returned by global lookup, destination membership, online component state and callbacks. Repeat with a destination that refuses a swap and with no replacement. |
| High · Waiting power registrations | `PoweredMachineBase` sets `_drawingPower` from actual cut-in and clears it on cut-out. `EndPowerDrawdown` and switching producers call `EndDrawdown` only if that flag is true. A producer can retain the subscriber while not delivering power. The retry path can begin again, then quit can forget the source without ending registration. A later cut-in can reach the quitted machine. [Consumer state](../../MudSharpCore/GameItems/Components/PoweredMachineBaseGameItemComponent.cs) · [Producer waiting lists](../../MudSharpCore/GameItems/Components/ProgPowerSupplyGameItemComponent.cs) | Start with an accepting but non-delivering producer, or cut power after admission. Quit before capacity returns. Assert a single end and zero later callbacks, including after switching to another source. |
| High · Socket composition and stale grid members | `PowerSocket.FinaliseLoad` uses `First` to choose a primary sibling producer. A missing/changed primary throws during fresh construction or boot finalisation. It starts drawdown before item login and has no symmetric socket quit/delete override. Similarly, grid outlet and feeder setters leave/join on reassignment, but their item teardown does not clear membership. Live grids can retain old component objects across unload or deletion. [Socket](../../MudSharpCore/GameItems/Components/PowerSocketGameItemComponent.cs) · [Outlet](../../MudSharpCore/GameItems/Components/ElectricGridOutletGameItemComponent.cs) · [Feeder](../../MudSharpCore/GameItems/Components/ElectricGridFeederGameItemComponent.cs) | Try zero/two valid siblings and a deleted endpoint on a live grid. Define a diagnostic for invalid composition and distinguish persistent grid affiliation from live membership. |
| Medium · Same-instance power reconnection | Powered-machine constructors subscribe to parent connect/disconnect. Quit releases parent and mounted-host subscriptions. Login refreshes the host and begins drawdown, but does not reattach those parent handlers. A source change on the same parent after relogin can go unnoticed once the bounded retry ends. A new object constructed from the row starts subscribed and hides the difference. [Topology subscriptions](../../MudSharpCore/GameItems/Components/PoweredMachineBaseGameItemComponent.cs) | Quit and log in the same machine object, wait past retry, then change the parent connector. Compare with a freshly constructed machine. |
| Medium · Incomplete connector replay | Generic independent links look up an already registered, colocated peer, use the first compatible connectable and clear pending entries. A dependent lookup may construct a peer on demand. The persisted connector type is read, but the replay calls ordinary `Connect`, which negotiates available connectors anew. A missing peer or multiple compatible ports can drop or change the intended connection. The graph drain discovers items, not discarded link records. [Connector restoration](../../MudSharpCore/GameItems/Components/ConnectableGameItemComponent.cs) | Start from a one-sided link, reverse discovery order and use two compatible ports with different roles. Assert the identity of both endpoints, both reverse references and clean dirty flags. |
| Medium · Child item versus child component | The ordinary container finalises and deletes an installed lock's **parent item**, but calls `Quit` and `Login` directly on the **lock component**. A held bag with a composite lock need not stop or resume that item's other components, effects, morph or registry membership. Item wounds similarly finalise lodged item parents, while ordinary item quit/login does not traverse that wound edge. Body-root wound handling follows a different path. [Container](../../MudSharpCore/GameItems/Components/ContainerGameItemComponent.cs) · [Item traversal](../../MudSharpCore/GameItems/GameItem.cs) · [Body item roots](../../MudSharpCore/Body/Implementations/BodyInventory.cs) | Use a carried container with a lock carrying a second timed component, and a wounded item with lodged ammunition. Check world membership and callbacks before and after character logout. |
| Medium · Late-only auction asset | In-process listing detaches an item without an item quit. Post-character auction loading may construct that same asset after the world graph drain and world login snapshot. Claim/cancel invokes item login before hand/floor placement and does not perform the missing graph finalisation. The item's connector state and clocks can differ before and after reboot. [Auction loading](../../MudSharpCore/Economy/Auctions/AuctionHouse.cs) · [Auction commands](../../MudSharpCore/Commands/Modules/EconomyModule.cs) | Define the escrow timing policy, finalise the asset after materialisation and activate it at the chosen boundary. Exercise a connected, timed asset reachable only through the auction. |
| Medium · Temporary copies and partially completed teardown | The temporary copy path still calls component copy constructors and finalisers. For example, copying a running fuel generator can start a heartbeat on the copy. `DeleteNative` detaches children and world state before the parent row delete commits. A callback or database error can leave a partially removed object with `Deleted` still false. Specialised spell/currency removal has additional guards. [Copy and delete](../../MudSharpCore/GameItems/GameItem.cs) · [Generator copy](../../MudSharpCore/GameItems/Components/FuelGeneratorGameItemComponent.cs) | Compare pending saves and heartbeat subscriptions before/after a discarded preview. Inject failure after child cleanup and before parent-row commit. Check the survivor and retry outcome. |

Other boundaries deserve explicit regression cases. The load-time finalisation flag is set before component callbacks and remains set if a callback throws. Effect persistence represents both an unscheduled effect and zero remaining milliseconds as zero, and restores a schedule only for positive values. A due saving effect can therefore lose expiry at the boundary unless the effect has its own deadline or reconciliation. On the ordinary health path, quit ends the health heartbeat, while login checks non-periodic wounds and does not restart a periodic item strategy on a reused instance. The default native item strategy is non-periodic. [Finalisation and health dispatch](../../MudSharpCore/GameItems/GameItem.cs) · [Health registration](../../MudSharpCore/GameItems/GameItemHealth.cs) · [Effect encoding](../../MudSharpCore/Effects/Effect.cs) · [Duration restoration](../../MudSharpCore/Framework/PerceivedItem.cs)

## Scope and evidence

A source scan of 286 C# files under `MudSharpCore/GameItems/Components` found 85 files declaring a `FinaliseLoad` override, 93 declaring `Login`, 107 declaring `Quit`, 121 declaring `Delete`, and 63 declaring `HandleDieOrMorph`. There were 77 files calling `TryGetItem` and 47 mentioning `HeartbeatManager`. Counts are per matching file and overlap. Inherited methods and helpers make these counts unsuitable as a pass/fail measure. The review followed the common item, component, registry, loader, room, inventory, save, effect and scheduler implementations and traced the distinct ownership, power and time families in the guide. It did not individually execute every component.

The initial reporting wrapper stopped before executing tests because the sandbox denied registry access during .NET telemetry startup. Both completed selections used the direct Release test runner with telemetry disabled. The test totals above come from the resulting TRX files.

The suggested acceptance world is small. Use one room with a bag containing a powered item, a second timed child that removes itself, a grid producer whose component ID collides with an unrelated item's ID, and a character with an installed composite lock. Add an auction-only asset and a revised item with populated ownership, skin, condition and timer fields. Compare the fresh world, same-instance logout/login, and fresh-process reload. Record item and component IDs, membership on both ends, callback counts, consumed fuel, remaining time and surviving rows. Use invalid cyclic ownership only in an isolated process with a bounded loader. These scenarios test different failure modes from the existing fast suite.
