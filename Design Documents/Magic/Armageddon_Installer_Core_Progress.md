## Ownership and failure behavior

`DatabaseSeeder/Assets/Manifests/Armageddon_Reviewed_Content.json` declares the partial package version, 21 stable identities, owned scalar fields, owned parameter/component relations and dependencies. The installer consumes and validates this embedded manifest. `SeederManagedRecord` remains the only ownership storage. Records capture package/module/version, native ID/revision, desired seed baseline, canonical baseline fingerprint, selected external bindings and dependencies.

The existing three-way reconciler updates unchanged seeded fields/links and preserves builder names, XML, formula edits, extra links, removed links, removed parameters, clones and unbaselined values. Actual builder values never become the desired stock baseline. Updates to unchanged owned links remove the old relation before binding its replacement. Prototype IDs are allocated above both surviving native rows and all packages' retained ownership logical IDs for that entity type, without filtering retired/missing records or revisions, inside the same serializable transaction. Each new ownership record also checks that its logical ID has no retained claim, including auto-generated spell/expression/prog IDs. Existing ownership IDs/revisions are retained; review metadata is not rewritten on rerun.

Unowned name/stock-identity collisions and competing ownership claims refuse takeover. Owned missing/retired rows, noncurrent statuses and later builder revisions block the entire batch without recreation or mutation. This conservative policy distinguishes intentional removal from this implementation's failed transaction: this slice never commits a partial graph. Legacy incomplete ownership requires explicit operator review rather than guessed repair. Existing dependents of deleted content are reported for restoration, retirement or rebind; the installer creates no new dangling dependency and does not pretend the module is complete. Native device validation continues to refuse an unresolved spell whitelist.

Content and ownership commit together in one transaction; no runtime factory transaction is nested or ambiently joined. Before-commit exceptions roll back the batch. Exceptions while commit is attempted return `CommitOutcomeUnknown`; a caller must reconnect and rerun. An acknowledged commit followed by failed confirmation returns `CommittedConfirmationFailed`. A restarted rerun resolves the already-owned identities without duplicates. Successful transaction completion can include reported preserved builder overrides; it is not a certificate that every custom override remains ready for runtime use.

No installer path reads or writes player enrolment, acquisition, mastery, opportunities, balances, character skills, inventory, item instances or charge banks. The native harness snapshots those domains solely to verify preservation.
