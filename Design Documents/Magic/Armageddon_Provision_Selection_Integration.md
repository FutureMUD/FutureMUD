## Frozen choice and live admission

Optional `FoodProfiles` and `Recipes` are versioned XML with orders 1–32, boolean(character) predicates and an explicit `always` fallback last. Every configured predicate and output must resolve, including nonselected candidates. Configured malformed XML is retained and fails closed on reload/clone. No configured profiles means the original fixed prototype/liquid behavior.

First matching profile wins. Food draws independently from that profile's approved pool once per selected grade. A private immutable token carries that original output sequence or recipe, recipient reference, physical actor frame, profile order and authored/candidate metadata stamp. Fresh casting copies adopt it before validation. Predicate callbacks still execute on live state; failure, nonboolean return, changed first match, callback movement or authored metadata drift refuses admission rather than selecting a replacement. Revalidation never draws food again. An advisory quote is a separate preparation; a new explicit Cast selects its own choices.

Application uses the original casting copy and rechecks live profile admission. Existing paid-failure reporting applies to refusal before mutation. Exceptions after a real first output retain the existing durable `NeedsReview` receipt and quarantine: no replay, automatic retry, refund or invented completion. Consumed/reviewed origin IDs refuse before preparation.

Independent review found that food confirmation originally preceded eligibility and lifetime callbacks. The correction runs all those callbacks before the final food confirmation, including permanent and cached-lifetime exits. That confirmation is the last callback-bearing admission in the item adapter; physical frame and profile/policy metadata checks follow every profile callback. The choice remains frozen. `ProvisionFoodAdmissionCastingTests` drives full Cast through the actual food adapter with seven counted draws and callbacks mutating only the third preparation; temporary/permanent/cached-lifetime eligibility changes and lifetime movement all refuse before Paying, debit or item creation. The dedicated native fixture repeats final eligibility and lifetime callback drift against real domain/SQL state. Qualification before this correction remains prior history.

## Combined final payment boundary

Independent rereview found that resource capacity callbacks run after the item adapter's final confirmation. A valid unchanged capacity result can conceal a changed first matching profile; ordinary native debit can execute the cap Prog again after Paying. The combined correction adds a single invocation-local selection payment boundary. Only invocations carrying a non-null prepared-selection token opt in. Fixed-output adapters and unrelated casts retain ordinary capacity behavior.

Capture raw actor/body/owner identity, spatial frame, state, entitlement lists, native trait values, target/input custody and components, liquid-container contents/open state/capacity, balances/holders, catalogue spell/capability/resource configuration, and an explicit focus's bank/reservation before the later live admissions. After committed Prepare and existing device admission, sample ordinary capacities if no device admission exists. Confirm each original frozen selection using live profile predicates without redrawing, then audit the raw captures, including the focus structural check. No reach, visibility, Applies, capability or capacity policy executes in that final audit. A changed selection or structural input refuses before creating the Paying operation.

Open `MagicResourceCapacityAdmission` only around the exact synchronous native payments. Capacity is consumed once by matching holder/resource/amount during `Character.UseResource`; ordinary reads before, within or after the batch stay live unless inside that exact admitted debit. Device scope remains intact. The sampled capacity is a payment admission value, not a global cache and not a fixed-point promise about arbitrary script state. Reexecuting capacity after final profile callbacks would reopen the same cycle, so the final debit consumes the admitted result instead. Application retains existing live effect validation and honest paid-failure/partial-output reporting; this does not make arbitrary authored Progs pure or replay them until they converge.

Actual-food full-Cast tests cover late real SimpleMagicResource cap-Prog first-match drift, final predicate mutation of balance/cap definition/native skill/location, focus custody/prototype mutation, and exact debit with an armed cap Prog that would change selection if rerun. They assert no Paying, no debit/output/operation and seven original draws on refusal; exact-debit tests preserve paid NeedsReview on an injected subsequent output fault and prove ordinary capacity becomes live after scope disposal. The four earlier adapter callback tests retain their assertions. Native qualification adds a real SimpleMagicResource/Character.UseResource case, contrasting a third-preparation cap mutation with a successful paid grade-seven cast with seven food outputs, no capacity callback during the debit and ordinary live capacity after it. Its outputs are explicitly removed without refund; receipt history remains.
