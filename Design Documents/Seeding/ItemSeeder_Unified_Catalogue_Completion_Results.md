# ItemSeeder unified catalogue completion results

The compiled catalogue migration and all locally available qualification are complete as of 24 October 2026. Fresh installation is 38.5% faster in the controlled local comparison, with a substantial build-time and executable-size cost. Stage 7's final executable-only execution gates remain open because of the Windows host policy and unavailable Linux/ARM hosts; publication inspection and DLL acceptance are recorded separately below. The approved scope is stages 3–8 of the [proposal](ItemSeeder_Unified_Catalogue_Implementation_Proposal.md); no additional era or industrial-food activation is included.

The current authoring contract is documented in [ItemSeeder](Seeders/ItemSeeder.md). Original [stages 1–2](ItemSeeder_Unified_Catalogue_Stage12_Results.md) and [first stage 3](ItemSeeder_Unified_Catalogue_Stage3_Results.md) receipts remain historical evidence.

- Ordinary and specialised content now uses typed, compiled C# records, with explicit fixed variants and era/profile/readiness metadata. All 15 original source/planning graphs are retained, including dormant vehicles and industrial research.
- A real legacy native authoring trace proved the first synthetic capture omitted navigation joins: 926 native recipes were missing and 36 synthetic-only recipes were not installed by the canonical legacy prerequisites. The corrected original-source capture has exactly the native legacy install's 11,703 pre-industrial craft identities. With 2,337 industrial capture recipes, the compiled selection has 14,040 recipes. The inactive 36 payloads and their old ownership are retained separately.
- The legacy native authoring trace has 11,704 calls for 11,703 craft identities. Its second tall-arrow-quiver recipe collides with the first. The compiled stock keeps the same first-registration behaviour and retains the suppressed Kushite payload explicitly for review.
- All 49,623 typed input/tool/success/failure serializers were checked against the original compact-string serializer. Independent full payload/knowledge/gate-metadata hashes pass for all 15 pre-industrial combinations. Generated IDs, trait selection and access-program bindings additionally require actual persisted native comparison; synthetic parity alone is insufficient.
- The compiled ownership inventory contains 43,825 identities. Compared with the original 42,756-entry inspection inventory, the corrected capture adds 890 craft, 168 program and 11 knowledge identities; other aggregate counts are unchanged. This inventory correction is distinct from activation: the native four-era selection still installs the original 34,981 ownership identities. The inspection JSON is recaptured with a source fingerprint; neither is a complete substitute for the rich catalogue data.
- The delivery full authoring capture contains 43,825 complete definitions, a field ledger, all source/planning graphs and an archive of 3,223 source files, including this final receipt. All archived source hashes match the checkout and all nine capture artifact hashes pass. The catalogue source fingerprint is `583bde2f55821c297afcad8e0d4249a01e37340b299ae30d251acff720431e3a`; the tested main DLL SHA-256 is `C2CA3AC91845A135B93E330363C9E6ACA9F0C029174CB5BA77281288B3138000`.

The converted data includes 7,872 direct historical definitions, 3,840 historical specifications, 5,298 other authored definitions, 178 medical/repair rows, 6,450 industrial ordinary definitions, 2,775 complete food definitions, 233 liquid definitions, 1,313 outfit graphs, five skins and 93 vehicle graphs. Counts describe overlapping source domains, not an additive total of installed items. Industrial graphs retain 464 food concepts, 307 dependencies, 26 serving scopes, 77 entries, 2,847 support rows, 100 outfit records and 35 profile bindings without activating their unfinished production programme. Decimal scale and source evidence are retained alongside values.

The ordinary build compiles these checked-in C# definitions directly. Content assemblies are bounded to keep compiler string heaps below the tested budget; single-file publication selectively precompiles all 80 catalogue assemblies. This trades more projects/source and executable size for avoiding runtime text parsing and large cold JIT costs. Existing common persistence and ownership writers remain; legacy authoring dispatchers, runtime item TSV readers and implicit fixed-recipe generation were removed.

## Controlled installer comparison

The controlled plan alternates three original and compiled fresh installs, restoring the same canonical prerequisites before each case. Each compiled install is followed by an unchanged rerun in a new process. All cases select Antiquity, Medieval, Renaissance and Early Modern with the neutral profile and full scope. No builds, tests or other database campaigns run concurrently. The measured interval is ordinary `SeedData` plus the final save, with no capture observers; fixture restoration, process startup and provider-metadata preparation are outside that interval. Peak working set is process-wide, and allocations cover the timed interval.

The frozen runtime-comparison binaries have main DLL hashes `33DA90BB0643968484C364C4DE84A315E34872FA2475E40A38AFF8ADF1E002F7` (original) and `C2CA3AC91845A135B93E330363C9E6ACA9F0C029174CB5BA77281288B3138000` (compiled). Both run through the same native measurement harness and installed .NET runtime. The original retains its six known zero-ID spoilage ownership bindings; recording its duration does not qualify those bindings as correct.

An original unchanged rerun is measured last, with a 900-second whole-process bound. If it exceeds that bound, the receipt records a censored observation including startup/provider preparation, rather than inventing a completed seeding duration or a median speedup. This final observation cannot affect the earlier paired measurements.

The nine completed samples have identical 34,981-record aggregate counts and their expected binary hashes. Each compiled sample has no nonpositive numeric ownership IDs. Three original fresh samples retain only the six known legacy spoilage bindings described above.

| Measurement | Median timed interval (range), seconds | Median cumulative allocations, GiB | Median peak application RAM, GiB |
| --- | ---: | ---: | ---: |
| Original fresh install | 498.07 (494.12–516.19) | 429.81 | 4.53 |
| Compiled fresh install | 306.33 (300.69–323.81) | 261.23 | 4.72 |
| Compiled unchanged rerun | 281.25 (278.46–287.75) | 228.89 | 2.70 |

The compiled fresh-install median is **38.5% lower**, and the observed runtime ranges do not overlap. Median cumulative allocations are **39.2% lower**; peak application RAM is **4.3% higher**. Allocations are all bytes allocated over the timed interval, not simultaneous RAM usage. These three local samples per group establish the observed improvement for this fixture and host, not a universal speed guarantee. They qualify ordinary DLL installation, not the final published executable's startup.

The original unchanged rerun did not complete within its 900-second whole-process limit and was terminated at 900.664 seconds. This is an explicitly censored observation, not a completed seeding duration; no exact rerun speedup percentage is claimed. The script exited successfully after recording that planned limit and shutting down the owned MySQL server.

## Build and publication costs

Three serial Release build pairs used existing, unchanged engine/persistence dependency outputs, no restore and one MSBuild node. Both compiled rebuild and unchanged incremental measurements include all 80 catalogue projects plus the main seeder. These measure seeder-owned compilation, not a clean build of the entire engine or solution.

| Measurement | Original median (range), seconds | Compiled median (range), seconds |
| --- | ---: | ---: |
| Rebuild | 13.87 (13.14–15.78) | 170.16 (168.61–170.64) |
| Unchanged incremental build | 1.74 (1.64–2.55) | 45.33 (45.30–45.95) |

This is a substantial build regression, including MSBuild traversal of the catalogue projects on unchanged builds. The retained design follows the approved runtime-first preference; its benefit must be assessed with the installer and cold-construction measurements rather than inferred from the source format. An embedded-data design could reduce compilation/project traversal at the cost of runtime parsing. No such architecture change is included here.

The original owned DLL occupies 40,761,344 bytes; compiled main plus 80 catalogue DLLs occupy 101,636,096 bytes (main alone 24,964,096). The main DLL hashes are stable across each design's three rebuilds. The compiled main is the exact DLL qualified above. The original source-build main hash is `3058FAB977F0DFB98254E241B864E0F1F153B941C847F7FC0B02AD5FAD8C7146`; it is distinct from the frozen original runtime-comparison harness binary and is labelled separately in the evidence.

Final cross-publication passes for `win-x64`, `linux-x64` and `linux-arm64`: each output contains exactly one executable and all 80 catalogue assemblies have native ReadyToRun headers. Their executable sizes are 342,242,224, 336,595,811 and 367,033,255 bytes respectively. The archived original Windows publication contains a 213,556,564-byte executable plus six other non-symbol files (233,498,427 bytes total excluding optional symbols); its complete output has 30 files and 270,872,939 bytes. The larger compiled/precompiled payload is an explicit runtime-speed trade-off. Local publication does not constitute a release or prove executable startup. Linux/ARM hosts are unavailable here, and Windows execution remains blocked as below.

## Windows execution and signing limit

The host's Smart App Control policy rejected an earlier unsigned Windows candidate (`E003…`). Read-only Code Integrity events match that candidate's exact executable SHA-256 and identify the enforced `VerifiedAndReputableDesktop` policy. The final publication (`74363C9473246FB8CD99C55CE5C5670002D31CE45FB3E94B518602E3A2DCFACF`) was inspected but not launched after that rejection. Security policy, exclusions and trusted certificate stores were not changed. Current native acceptance uses the ordinary DLL through `dotnet`; final executable-only bootstrap/install/rerun remains unverified because the host execution blocker is unresolved.

No paid signing integration or account was configured. Microsoft Store MSIX distribution is a free signing option, but requires separate packaging, certification and launch/storage/runtime qualification and does not sign the portable EXE. SignPath Foundation's free programme requires an OSI-approved licence, which FutureMUD's current licence does not satisfy. See the [release process](../Core/FutureMUD_Release_Process.md#windows-signing-and-free-distribution-options). No Store submission, licence change, tag or release publication was performed.
