# Sharing expensive test setup in FutureMUD

The changes and final measurements are recorded under [Implemented fixtures and measured results](#implemented-fixtures-and-measured-results).

## Where the time goes

The strongest candidates are the terrain foundations used by both the core terrain and autobuilder tests, the prerequisites for Armageddon protection and heritage, and spell-factory registration in the runtime tests. Each has a specific boundary before the behaviour being tested. They can be addressed within their existing projects and test categories.

The baseline is commit `0a8e8281fb561742b948b8a3dc8f56c369b244fb`. The three CI workflows below ran that revision with the default category exclusions. ## Local comparison

Disposable copies of the test projects exercised the same named cases and DataRows on Windows, .NET 11.0.100, Debug. Each group ran four times in separate processes with already-built binaries, in the order control, shared, shared, control. The terrain control used the common equivalent foundation builder for the nine eligible rows. The S4 and heritage controls built their original prerequisite for every consumer. The shared variants used the existing InMemory snapshot mechanism. Test data, calls under test, assertions and category selection were the same on both sides.

| Group | Full command seconds, control → shared (first pair / second pair) | Measured setup seconds, control → shared | Managed GB allocated during setup, control → shared |
| --- | --- | --- | --- |
| Terrain and autobuilder, 10/10 passed each run | 68.5 → 23.2 / 30.3 → 19.9 | 25.6–27.3 → 14.0–14.4 | 48.8 → 12.1 |
| S4 protection, 14/14 passed each run | 37.4 → 30.5 / 35.2 → 25.3 | 25.7–27.4 → 15.9–16.8 | 30.4 → 2.9 |
| Heritage family, 24/24 passed each run | 72.2 → 61.6 / 65.8 → 58.1 | 21.1–21.5 → 11.1–12.1 | 26.6 → 2.2 |
| MagicEngineV4, 337/337 passed each run | 37.9 → 32.7 / 31.2 → 26.6 | 2.03–2.21 → 0.19–0.29 | 0.87–0.88 → 0.016 |

Setup spans include creation of required baselines, first capture and every restore. The terrain row that must start without terrain remains in the group time and is outside these spans. Allocation deltas use process-wide `GC.GetTotalAllocatedBytes(true)`, in decimal GB. They measure allocation traffic, which can exceed available RAM as the GC reclaims objects. Command timings include host startup, test bodies, disposal and runner overhead. The first terrain control command took 68.5 seconds for 31.5 summed case-seconds. The second pair and setup measurements give a more useful indication of the repeatable difference. Neither peak resident memory nor CI end-to-end savings were measured by these local probes.

There is a cost to filtering down to one consumer. In the first S4 comparison the cold prerequisite took 9.7 seconds either way. Capturing it added 6.0 seconds, and subsequent restores typically took tens of milliseconds. Sharing paid off over 14 consumers. A one-off install or a small synthetic fixture has a different trade-off.

For V4, the control instrumented the two registrations once per row and the candidate once per class. The probe wrote a timing record after each measured call. Attribute about two seconds and 0.86 GB per focused run to repeated registration. The larger difference in command times includes logging overhead and runner variation. The rest of the 337 scenarios still executed.

All four comparisons matched the names, multiplicity and passing outcomes of every row on both sides, totalling 385 distinct cases per pass. A separate shared-factory run included item magic casting, prepared selection casting and stock operation reporting. Its first attempt gave the timing probe a relative output path, which failed during V4 class initialization. Correcting the probe path and running the same selection produced 414 passed, zero skipped. The original and corrected TRX files, per-phase measurements and hosted receipts are retained locally under `.artifacts/fixture-audit/`.

## Implementation plan from the review

1. **Start with terrain and autobuilder.** Extract their common fixture under DatabaseSeeder Unit Tests and keep both account variants lazy. Use the existing persisted-scalar snapshot and let the caller supply equivalent options for a new, uniquely named database. The original snapshot helper hard-coded disabled null checks and omitted the terrain fixture's transaction-warning configuration. The terrain prototype retained strict null checks and the ignored InMemory transaction warning. Keep the account before foundation seeding wherever the original case supplied it. [Snapshot implementation](../../DatabaseSeeder%20Unit%20Tests/InMemorySeederSnapshot.cs) · [Database lifetime](../../DatabaseSeeder%20Unit%20Tests/OwnedInMemorySeederContext.cs)
2. **Give S4 a named prerequisite fixture.** Replace the private reflection call with an internal factory that builds the Simple/no-classes baseline lazily. Restore it for each test before the first S4 call. Keep the baseline scoped to that input until measurements justify other combinations. Preserve the extended path that configures combat before installing weapons. Reuse the existing snapshot-isolation tests for scalar values, shadow foreign keys, joins and generated keys, adding a representative terrain or S4 invariant where the existing coverage ends. [Existing isolation checks](../../ArmageddonSeeder%20Unit%20Tests/ArmageddonStockSpellInstallerTests.FixtureIsolation.cs) · [Custom combat path](../../ArmageddonSeeder%20Unit%20Tests/ArmageddonStockSupportInstallerTests.MasterIntegration.cs)
3. **Apply the same boundary to heritage.** Build the common skill/chargen scaffold once, then restore a private copy for each of its 23 consumers in the measured group. Keep the pure attribute-selection case independent. The helper also has consumers in player health, physiology and guard/vendor tests. Include those callers before changing its default behaviour. The measured gain already comes from sharing the scaffold, so a second cache of fully installed Heritage data adds complexity with no measured justification.
4. **Verify scope and lifetime before expanding.** Keep seed and snapshot ownership inside the test assembly. Dispose the source store once captured, dispose each clone after its borrowers, and release large retained snapshots at the end of their consumer scope. Compare actual class and project times with the default filters, then run the relevant opt-in callers if their helper changes. Check that a single filtered row still runs in a fresh host, that one clone's edits cannot affect the next, and that a fresh install, broken prerequisite and rerun still exercise their original entry points.

**Runtime follow-up.** Change V4's two explicit registrations from test initialization to class initialization. Check the complete core project, including tests that overwrite factory delegates and restore them in cleanup. Apply the same change to V2 or V3 only after checking their overrides and measuring those classes. This change is independent of the seeder work and can land separately.

For repeat measurements, build once and run each comparison in fresh test hosts. The matching class filters are `FullyQualifiedName~UsefulSeederAutobuilderTests|FullyQualifiedName~CoreDataSeederTerrainTests`, `FullyQualifiedName~S4ProtectionSupportTests`, and `FullyQualifiedName~MagicEngineV4Tests`. For heritage, select the five classes named in the table. Use the same configuration, category filter and DataRows on both sides. Record the full invocation, first baseline creation, snapshot capture, per-test restoration and cleanup. Retain the TRX results to check outcomes and identification of every row. For a broader rollout, compare peak testhost memory and CPU as well as managed allocations, and compare the slowest host on each OS using the [existing CI receipts](../../.codex/references/test-execution.md#ci-timing-evidence).

## Implemented fixtures and measured results

The terrain and autobuilder tests share two lazily captured foundations, chosen by whether the original world has a seeder account. Each restored database has a unique owner, strict null checks and the original InMemory transaction-warning configuration. The question-availability case still starts with an empty terrain catalogue. The new opt-in terrain regression writes to one copy, reads the original value from a second, disposes the writer, and checks the account variants. [Terrain fixture](../../DatabaseSeeder%20Unit%20Tests/TerrainSeederFixture.cs) · [Isolation regression](../../DatabaseSeeder%20Unit%20Tests/CoreDataSeederTerrainTests.cs)

Armageddon S4 and the matching Simple/no-classes support cases share the persisted pre-S4 prerequisites. The custom combat setup and other mode/class combinations keep their original setup. Heritage and its other consumers share the skill/chargen scaffold before Heritage installation. All writers get independent stores. MagicEngineV4 registers the two factory sets once per MSTest class.

The focused groups together saved 20.18 host-seconds and 93.09 GB of allocation traffic. These groups overlap the full-project runs. All default cases matched by class, name, multiplicity and outcome on both sides. The 101 skips comprise 98 private Armageddon corpus cases and three Unix permission cases on Windows. Four fresh-host single-case checks passed, including the terrain isolation regression. All 43 selected stock-support and snapshot cases passed with extended selection.

Two more alternating-order comparisons isolated the V4 registration change using otherwise identical linked-source projects and the process-exit hook. All 337 cases passed in every host. Pair one went from 33.34 to 32.06 seconds, and pair two from 29.07 to 27.12 seconds. Both allocated about 0.86–0.89 GB less. Together with the first focused comparison, these runs support a consistent allocation saving and a small, variable time effect. The complete core project took 10.81 seconds longer in its single after run.

The three full hosts together saved **28.79 seconds (7.1%) and 98.65 GB of managed allocations (23.2%)**. Peak working set increased by 97 MB in DatabaseSeeder. Each complete project was timed once per revision, so run-to-run variation is included. Parallel hosted CI was outside this comparison. TRX, elapsed and resource receipts are retained locally under `.artifacts/fixture-implementation/`.
